# Cross-library request validation matrix, OpenAPI 3.2

Every case against every library: what each one was asked, what it answered,
and where the specification says there is a right answer at all. Conformance
comes first, then the cases the specification leaves open. `README.md` in this
directory says what a case is and what the two kinds mean.

Generated by `pnpm render-md`. Every cell traces to
`report/libraries/<slug>.json` by case id and library name. Libraries appear
in alphabetical order of package name, read from its first letter or digit,
so an ecosystem's leading punctuation does not decide who comes first.

In this file: [the libraries measured](#libraries-measured), the
[conformance outcomes](#conformance) with
[every case written out](#conformance-cases-in-full), and the
[divergence findings](#divergence). Case ids link to the case in full,
and library names link to that library's own page.

No conformance outcome is totalled across libraries here. Libraries are
asked different numbers of cases, so each library's outcome counts have a
denominator of their own, and a column of them would rank libraries against
denominators they do not share. Across libraries this report says which case
produced which outcome, and outcome counts appear only in a single library's
own file, beside the denominator they came from.

Other counts are published where they describe rather than score: the
specification surface in `coverage.oas32.md`, and what each
library exposed in
`capabilities.md`. Nothing in those is measured against an expected answer,
which is what separates a description of a library's shape from a verdict on
its correctness.

Whether these measurements still match the libraries is established only by
`pnpm check:containers`, which rebuilds every container and re-asks every
question. The fast gate rebuilds this file from the committed measurements,
so it says this file matches that JSON and says nothing about the JSON. The
file the run writes to record when it happened is not committed, so this
file carries no measurement date: the version and image id below say what was
measured rather than when.

#### Cookie parameters

##### `cookie-cookie-array-canonical-explode-oas32`

cookie, cookie style, array, explode defaulted true, canonical. Expected: **accepted**.

Repeats the cookie name once per item, separated by the semicolon and space cookies use. The style table gives exactly these crumbs.

Request: `GET /t`

Header: `Cookie: p=blue; p=black; p=brown`

Every rule the expected verdict rests on, OpenAPI 3.2:

[parameter-style](https://spec.openapis.org/oas/v3.2.0.html#parameter-style)

> Describes how the parameter value will be serialized depending on the type of the parameter value. Default values (based on value of in): for "query" - "form"; for "path" - "simple"; for "header" - "simple"; for "cookie" - "form" (for compatibility reasons; note that style: "cookie" SHOULD be used with in: "cookie"; see Appendix D for details).

[parameter-explode](https://spec.openapis.org/oas/v3.2.0.html#parameter-explode)

> When this is true, parameter values of type array or object generate separate parameters for each value of the array or key-value pair of the map. For other types of parameters, or when style is "deepObject", this field has no effect. When style is "form" or "cookie", the default value is true. For all other styles, the default value is false.

[style-values](https://spec.openapis.org/oas/v3.2.0.html#style-values)

> | cookie | primitive, array, object | cookie | Analogous to form, but following [RFC6265] Cookie syntax rules, meaning that name-value pairs are separated by a semicolon followed by a single space (e.g. n1=v1; n2=v2), and no percent-encoding or other escaping is applied; data values that require any sort of escaping MUST be provided in escaped form. |

[style-examples](https://spec.openapis.org/oas/v3.2.0.html#style-examples)

> | cookie | true | color= | color=blue | color=blue; color=black; color=brown | R=100; G=200; B=150 |

[schema-object](https://spec.openapis.org/oas/v3.2.0.html#schema-object)

> The Schema Object allows the definition of input and output data types. These types can be objects, but also primitives and arrays. This object is a superset of the JSON Schema Specification Draft 2020-12.

explode is left out and defaults to true for the cookie style, so the exploded row applies, and it writes an array as the name repeated with a semicolon and a space between the pairs. The request carries that, character for character.

Varies: nothing. Holds constant: identifier is the declared one; wire shape matches the declared style; explode is left to the version's default.

## Divergence

The specification requires no particular answer to these. The table reports what
each library returned. No cell is a failure and nothing here is attributed to
anyone.

The value column is what the library parsed, which is not always what an
application would receive: some libraries expose parsed values even for a
request they rejected, and a rejected request reaches no handler.

Each row holds two separate results, and the key for both is:

| result | meaning |
| --- | --- |
| `accepted`, `rejected` | the verdict the library reached on the request |
| `raised, no verdict` | it threw instead of answering, which is attributable to it and is not a rejection: an application would have seen an exception |
| `not asked (<reason>)` | it was never given the case, because it does not perform the stage the case probes; `capabilities.md` has the reason in full |
| `harness error` | an error in the adapter or the harness rather than an answer from the library |
| `` `{"p":"blue"}` `` | the values it handed back, as it returned them, with the vantage they were read from |
| `not exposed by this library` | it reached a verdict and publishes no call that returns deserialized values, which is a fact about the library rather than about this request |
| `none reached` | it does expose values, and produced none here |

A case marked **answered in the values** is one the verdict cannot carry: every
reading of the specification accepts the request, and what separates them is
what comes back. A library exposing no values reaches a verdict on such a case
and answers nothing by it, so read those tables down the value column alone.

### Cookie parameters
