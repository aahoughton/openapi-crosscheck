# Fitness as a request validator

Generated by `pnpm render-md`. What each library does for itself, stage by
stage of the request-validation pipeline, and therefore what a caller supplies.

This is a different question from the matrix files. Those ask whether a library
reads the specification correctly when it is fed at the boundary it accepts.
This one asks how much of the pipeline you would be writing yourself. Nothing
here is scored or ranked: a library owning fewer stages has a different shape,
and a caller whose framework already splits the request may want that shape.

`owned` means the library does it. `caller` means the library requires it to
have been done already, so the specification rules governing that stage are
the caller's to get right, and the second half of this report names them.

A citation listed under a stage is a rule some case probing that stage rests
on. A case's verdict can rest on rules governing a neighbouring stage too, so
read the list as what the corpus knows about that stage rather than as the
exact set of rules governing it and nothing else.

`style and explode` and `content media type` are the two ways a parameter's
serialization can be specified, and the specification requires each parameter to
use one. They are separate columns because a library can do one and not the
other, and one column covering both cannot say so.

A library is asked a case only when it owns the stage that case probes and
every stage between that one and the verdict. Stages upstream of the probe can
be filled in by the harness, identically for everyone and recorded on the cell.
Stages downstream cannot: those produce the verdict, and a harness that
deserialized a style or validated a schema on a library's behalf would be
grading its own work.
